# Динамические участники — обновление опубликованного gooffice

## Модель и совместимость

Один документ `team/registry` хранит `version: 1`, карты `profiles`, `names`, `colors`, `usedIds` и массив `order`. Профиль: `{id, name, nameKey, color}`. `order` определяет только порядок шапки. `names` связывает имя в нижнем регистре с ID, `colors` резервирует цвет, `usedIds` навсегда сохраняет использованные ID, включая удалённых участников.

Новый профиль добавляется транзакцией в конец реестра. Правила проверяют максимум 20, неизменность старых профилей, уникальность имени и цвета, точную схему и добавление только одного нового ID. Конкурирующие транзакции повторяют чтение; последнее место нельзя занять дважды. Новые ID имеют вид `p_` + 32 шестнадцатеричных символа UUID. Цвет выбирается случайно из свободных цветов фиксированной палитры. Имя: 1–24 русские/латинские буквы, внутренние пробелы и дефисы; края обрезаются, повторные пробелы сводятся к одному, регистр не различается. `е` и `ё` — разные буквы.

Изначальные `alan`, `denis`, `anya`, `dasha` сохраняют имена, цвета и порядок из `data.js`. Этот список теперь служит только начальным наполнением, а рабочий список приходит через `onSnapshot`. Идемпотентная инициализация создаёт только отсутствующий реестр с точными исходными четырьмя профилями, никогда не перезаписывает существующий документ и не изменяет отметки.

Отметки остаются по прежним путям `days/YYYY-MM-DD/marks/memberId`, с прежними серверными временными метками и сортировкой seconds → nanoseconds → ID. Запрос каждого дня использует `where(documentId(), 'in', currentIds)` и `limit(20)`. Поэтому старые отметки удалённых профилей не занимают места среди результатов действующих участников. Правила допускают ограниченный list до 20, создание/удаление отметок существующих профилей и запрещают update отметок. Часовой пояс — Europe/Moscow. Выбранный ID остаётся в прежнем ключе localStorage.

## Точный порядок выпуска

1. Сохраните резервную копию опубликованных правил и файлов сайта. Сохраните данные Firestore доступным вам способом; не удаляйте и не переименовывайте существующие отметки. Проверьте проект `gooffice-5f6c0`, базу `(default)`.
2. Локально выполните `npm ci`, `npm test`, `npm run test:rules` (для эмулятора нужна Java 21+). Команда проверки использует только `demo-gooffice-rules` и localhost. Она не публикует правила.
3. В Firebase Console → Firestore Database → Rules замените правила целиком содержимым `firestore.rules`, проверьте редактором и опубликуйте вручную. Не оставляйте дополнительные глобальные разрешения. **Правила обновляются первыми.** До появления реестра они продолжают разрешать прежние четыре ID; старые запросы `limit(4)` также остаются разрешены.
4. После публикации правил выполните вручную из папки проекта `node tools/initialize-participants.mjs --initialize`. Это единственная команда в этом документе, которая создаёт документ в рабочей базе. Без `--initialize` скрипт ничего не записывает. Повторный запуск при существующем реестре ничего не меняет. При ошибке остановитесь до публикации нового сайта.
5. В Console → Data откройте `team/registry`: убедитесь, что присутствуют четыре исходных профиля, их старые ID/цвета, порядок `alan, denis, anya, dasha`, соответствующие карты names/colors/usedIds. Сверьте несколько старых отметок с резервной копией. Если реестр уже существовал, скрипт его не меняет. Сохраните и проверьте все его профили. Если старая версия записала имена с повторными пробелами, перед выпуском проверьте, что после нормализации нет совпадений. При необходимости согласуйте исправление и атомарно обновите поля name/nameKey и соответствующие ключи names, сохранив ID и цвета. Правила проверяют уникальность по каноническим ключам names.
6. Подготовьте публикацию в отдельной пустой папке. Скопируйте туда только `index.html`, `styles.css`, `app.js`, `data.js`, `visual-effects.mjs`, `firebase-init.mjs`, `firebase-config.mjs`, `cloud-store.mjs`, `participants.mjs` и `assets/fonts/` с сохранением путей. Проверьте состав папки и опубликуйте только её содержимое. `review/` предназначена для локальной проверки и исключена из Git. Не загружайте корень проекта целиком: `.gitignore` не действует при прямой загрузке файлов на хостинг. Публикацию выполняет владелец проекта.
7. Обновите старые открытые вкладки. Проверьте на двух устройствах исходные отметки/выбранный профиль, создание нового участника, одинаковый цвет и порядок шапки, отметку и отмену нового участника, перезагрузку. Для проверки лимита используйте эмулятор, не заполняйте рабочий список тестовыми людьми.

Старая версия сайта с новыми правилами продолжает обслуживать исходные четыре профиля, но не узнаёт новых участников без обновления. Новые ID начинаются с `p_`, поэтому прежние `limit(4)`-запросы по ID не вытесняют исходных участников новыми. До ручного удаления профилей обновите все старые вкладки. Для отката интерфейса сохраняйте совместимые новые правила; возврат старых правил заблокирует новые ID. Самостоятельно никакие правила, данные или файлы сайта в рамках разработки не публиковались.

## Ручное административное удаление

1. Обновите вкладки до новой версии, сохраните резервную копию `team/registry`. На время ручного редактирования договоритесь не добавлять участников: Console обходит клиентские правила, не затрите параллельное добавление старым содержимым документа.
2. В Firebase Console → Firestore Database → Data → `team/registry` найдите ID, `nameKey` и цвет нужного профиля.
3. **Одним сохранением документа** удалите `profiles.<id>`, ID из массива `order`, запись `names.<nameKey>` и запись `colors.<цвет>`. Остальные поля и профили сохраните.
4. **Оставьте `usedIds.<id>: true` навсегда. Не удаляйте сам документ реестра.** Это предотвращает повторное присвоение старых отметок другому человеку. Не переименовывайте старый ID и не подменяйте профиль новым именем.
5. Проверьте исчезновение профиля на двух устройствах. Если он был выбран, новый интерфейс сбросит выбор и предложит выбрать другого. Место, имя и цвет освободятся; новый участник с тем же именем получит новый ID и начнёт без чужих отметок.

Отметки удалённого ID можно оставить: новая версия их не запрашивает и не показывает. Административная очистка этих документов — отдельная операция после резервного копирования. Если появится отдельный административный инструмент, он должен менять реестр атомарной транзакцией и сохранять использованный ID в usedIds. Бот для сводок только читает данные.

## Контракт чтения для Telegram-бота

| Путь | Поля и типы |
| --- | --- |
| `team/registry` | `version`: число 1. `profiles`: карта ID → объект со строками `id`, `name`, `nameKey`, `color` (CSS hex). `order`: массив строк ID для порядка в шапке. `names` и `colors`: карты строк → ID; `usedIds`: карта ID → boolean. |
| `days/{YYYY-MM-DD}/marks/{memberId}` | `memberId`: строка, совпадает с ID документа. `createdAt`: серверный Firestore Timestamp. `dayStart`: Firestore Timestamp с датой в 00:00 UTC для кодирования календарного дня. |

1. При каждом построении сводки прочитайте `team/registry` напрямую. Для каждого `memberId` берите отображаемое имя из `profiles[memberId].name`. Имена новых участников подтянутся без правок бота. Если реестр отсутствует, считайте это незавершённой настройкой и повторите чтение после инициализации.
2. Для ежедневной сводки и обновления сообщения определите «сегодня» в `Europe/Moscow` на момент построения. Окно сводки — сегодня и следующие шесть календарных дней включительно. Читайте подколлекции `marks` по прямому пути, поскольку родительский документ `days/{date}` может не существовать. Можно фильтровать по ID документа с `in` по действующим ID и `limit(20)`. При пустом списке ID пропустите запрос. [Firestore поддерживает до 30 значений для такого запроса](https://firebase.google.com/docs/firestore/query-data/queries#in_not-in_and_array-contains-any).
3. Если профиль из отметки отсутствует, пропустите эту отметку: удалённый ID не переиспользуется. Сортируйте отметки по `createdAt.seconds`, затем `createdAt.nanoseconds`, затем по ID документа. Показывайте все семь дат в хронологическом порядке. В заголовке дня укажите количество действующих отметок; при нуле выведите «никого» без строки с именами.
4. Worker с сервисным Google OAuth использует права IAM, а не клиентские Firestore Rules. Для него достаточно чтения реестра и отметок; учётные данные остаются на стороне Worker. См. [правила запросов и IAM](https://firebase.google.com/docs/firestore/security/rules-query).

## Ограничения

Без авторизации любой посетитель может занять свободное место допустимым именем и менять отметки любого участника. Правила защищают схему и предел 20, но не подтверждают личность, не обеспечивают приватность и не ограничивают частоту запросов/расходы. Нельзя удалить, переименовать или перекрасить профиль через клиент. При ошибке связи добавление не считается успешным; после подтверждённой записи и последующего сбоя загрузки приложение сообщает, что профиль уже создан, и предлагает обновить страницу.

Карты usedIds растут при административных удалениях. При очень большом количестве замен потребуется новая схема до достижения ограничения Firestore в 1 MiB на документ. Реестр рассчитан на небольшую команду, а не на публичный каталог. Автоматическая инициализация новой страницы является страховкой; рекомендуемый выпуск выше создаёт реестр заранее.
